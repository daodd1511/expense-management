The app has quietly graduated from "in-memory prototype" to a real client–server product. Every data operation flows through the backend; the Supabase anon key never reaches the browser for data access.

02 What's good

These are genuine strengths worth protecting — several are unusual for a personal project.

End-to-end type safety

packages/shared defines Zod models, DTOs, and row mappers used by both sides. The API even re-validates rows Supabase returns after insert/update — data corruption gets caught at the boundary, not in the UI.

Security posture

Full-proxy design: anon key out of the browser for data, JWT verified against Supabase JWKS, and every single query filters by owner_id. No route forgets it.

Two layouts, both first-class

Mobile (FAB, bottom sheets, swipe actions) and desktop (sidebar, dense tables, drawers) are purpose-built rather than one layout stretched — and feature parity is real.

Subscriptions done thoughtfully

Due detection, a double-log guard that checks the previous cycle window by subscriptionId, and a server-side one-tap /log endpoint that creates the transaction and advances the due date.

i18n with compile-time parity

TranslationKey is inferred from the Vietnamese dictionary, so a missing English key is a type error. Vietnamese-first is consistent with the actual user.

Error handling shipped, with tests

ErrorBoundary, offline banner, centralized mutation error handler, useFormSubmit — all covered by the 39-test web suite plus API route tests. CI runs typecheck + tests before deploy.

Design point of view

PRODUCT.md has anti-references ("not a SaaS dashboard, not a bank app"), OKLCH semantic tokens, numbers-lead principles. Most side projects never write this down.

Schema integrity in the DB

The category hierarchy (2-level cap, type must match parent) is enforced by a Postgres trigger, not just app code — the DB can't be corrupted by a buggy client.

03 What's missing — feature gaps

Ordered by value against the product's own goal: "open the app, know within 10 seconds whether the household is on track." Today that answer stops at aggregates — you can see that you overspent, but not why.

PriorityGapWhy it matters
P1 Reports & category drill-down The entire Reports section is unbuilt: no monthly report, no tap-a-chart-segment → see the transactions behind it, no year-over-year. Drill-down is the single highest-value missing interaction — it's what turns the dashboard from a display into a tool.
P1 Receipt attachment regressed The schema has the field and rows render a paperclip, but TransactionForm hardcodes receipt: null — there is no upload UI. It silently fell off during BE integration. Rebuild on Supabase Storage (never base64 into the row).
P1 Export / backup Data is now real and server-side, and there's no user-facing escape hatch — no CSV export, no JSON backup/restore. For a personal finance record this is a trust feature, not a nice-to-have.
P2 Subscription auto-log / reminders Due detection only runs client-side when the app is open. A scheduled job (pg_cron or a cron on the VPS hitting the API) + notification would close the loop — right now a subscription silently goes overdue if you don't open the app.
P2 Household sharing PRODUCT.md says "Thomas and optionally a household partner," but the data model is strictly single-owner (owner_id = JWT sub). Sharing needs a household/membership concept — a schema-level decision that gets more expensive the longer real data accumulates.
P2 Budget lifecycle Budgets display well, but there's no rollover (carry unused amount) and no near-limit alerts. Budgets that never react are read-only decoration by mid-month.
P3 Offline write queue The PWA is online-only; logging a purchase with no signal fails. The pieces for a mutation queue (TanStack Query + Zod schemas) already exist. Real work, but the primary use case is "log a purchase after shopping" — often exactly when connectivity is worst.
P3 Desktop power features Keyboard shortcuts (N = new transaction, / = search) and a command palette are planned but unbuilt. Cheap wins for the "reconcile at the end of the week" desktop session.
P3 Small planned items Account reorder, currency format preference, PIN/biometric lock, pull-to-refresh, per-locale number formatting. None urgent; batch them opportunistically.

04 What could be better — technical debt

Nothing here is on fire; two items (docs, data fetching) compound with time and should be scheduled deliberately.

HIGHCLAUDE.md and FEATURES.md describe an app that no longer exists

CLAUDE.md still documents the pre-monorepo SPA: in-memory store seeded from lib/data.ts, "no test suite exists," commands without workspaces, paths like lib/store.tsx that are now packages/web/src/core/. FEATURES.md lists persistence as unbuilt. In an agent-driven workflow the stale CLAUDE.md misleads every session — this is the cheapest high-leverage fix in the repo.

CLAUDE.md · docs/FEATURES.md
HIGHAll transactions fetched forever, no month scoping

The API supports ?month=, but the FE fetches the full transaction history on every load and recomputes monthSummary/expenseByCategory over all of it. Fine at hundreds of rows; a couple of years of daily household use will bloat payloads, cache invalidations, and derived computation together.

packages/web/src/features/transactions/db.ts · core/store.tsx
MEDstore.tsx is a god-context shim from the in-memory era

It wraps ~20 TanStack Query hooks into one context value, so any data change re-renders every consumer, and it hides Query's own loading/error states behind a single loading boolean. Migrate consumers to feature queries directly; keep only the pure derived selectors.

packages/web/src/core/store.tsx (290 lines)
MEDBulk delete makes N requests despite a bulk endpoint

deleteTransactions does Promise.all of per-id deletes while DELETE /api/transactions (bulk) and the useDeleteTransactions hook sit unused. N round-trips, non-atomic, N cache invalidations. Known and noted in HANDOFF; worth actually fixing.

core/store.tsx:139 · api/src/routes/transactions.ts:110
MEDSubscription /log is not atomic

The endpoint inserts the transaction, then updates next_due_date in a second call. A failure between the two leaves a logged payment with a stale due date. The double-log guard mitigates the visible symptom; a Postgres function (RPC) would make it actually atomic.

api/src/routes/subscriptions.ts:58–126
MEDTwo timezone policies

The API computes month bounds in UTC; the FE's inCurrentMonth and daysUntilDue use local time; /log stamps dates from server UTC. In UTC+7, rows near month boundaries can land in different months depending on who's counting. Pick one policy (user-local, since it's a household ledger) and centralize it.

api/routes/transactions.ts:16 · core/store.tsx:294 · subscriptions/helpers.ts
LOWMoney-math has no tests

Forms and pickers are well covered, but computeBalance, monthSummary, and the subscription due-window logic — the arithmetic the whole product exists for — have zero unit tests. They're pure functions; testing them is an afternoon.

core/store.tsx · subscriptions/helpers.ts
LOWAPI dev loop has no watch

pnpm dev for the API builds once and runs dist/ — source edits don't reload. Known, unfixed; a tsx watch or esbuild watch mode is a one-line change.

05 Suggested order of attack

Sequenced so each step protects or unlocks the next; sized for the existing spec-per-feature workflow.

Re-baseline the docs

Rewrite CLAUDE.md's architecture/commands sections and sync FEATURES.md to reality. An hour of work that de-risks every agent session and every spec that follows.

Data-layer hygiene spec

One spec bundling: month-scoped transaction fetching, bulk-delete wiring, store.tsx dissolution into feature queries, one timezone policy, unit tests for the money math. Do this before Reports — reports are derived data, and you want them built on the scoped queries.

Reports + drill-down

Monthly report, tap-through from any chart segment or budget bar to its transactions, CSV export. This is the feature that pays back the whole backend investment.

Household model — deferred

Explicitly parked until all core functions are present. When picked up: decide the sharing schema (household + membership vs. shared owner) before the partner UI.
