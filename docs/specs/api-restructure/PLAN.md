# API Restructure — Plan

Fourth and final spec of the batch. A **behavior-preserving** migration of `packages/api`
from flat route files (DB calls, validation, and business logic inline in handlers) to a
**layered feature architecture** (controller / service / repository / schema per domain).
Runs **last**, after `foundation` → `feature-ux` → `polish` all merge, so it restructures
the routes in their final behavioral shape. EXECUTION.md generated by `spec-plan` at
activation (it must inventory the then-current routes — including the `analytics` endpoint
added in `feature-ux` and the `log_subscription` RPC from `foundation`).

## Motivation

Route files carry everything inline (`categories.ts` is 266 lines: HTTP + hierarchy
validation + DB + error mapping). Separating concerns makes each layer testable and keeps
handlers thin. This is internal refactor only — **no behavior change**, every existing test
must still pass at the HTTP level.

## Target structure

```
packages/api/src/
├── index.ts                 # entry point (server bootstrap)
├── app.ts                   # create + wire the Hono app
├── config/
│   ├── env.ts
│   └── supabase.ts          # moved from db/supabase.ts
├── middleware/
│   ├── auth.ts              # exists
│   ├── logger.ts            # new — pino structured logging
│   └── error.ts             # new — centralized handler (absorbs mapDbError logic)
├── features/
│   ├── accounts/            # routes, controller, service, repository, schema, types
│   ├── transactions/
│   ├── categories/
│   ├── budgets/
│   ├── subscriptions/       # carries the log_subscription RPC (service layer)
│   ├── favorites/
│   └── analytics/           # exists by spec-4 (added in feature-ux)
└── lib/
    ├── jwt.ts               # extracted from middleware/auth.ts
    └── response.ts          # from lib/http.ts (json helpers)
```

## Decisions

| Topic          | Choice                                                                                                                                                                                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Layer split    | `controller.ts` = thin HTTP handlers; `service.ts` = business logic (hierarchy rules, RPC calls, balance reduction); `repository.ts` = Supabase access via **shared mappers**; `routes.ts` = route wiring.                                            |
| Schemas / DTOs | `packages/shared` row/model schemas + mappers stay the **single source of truth** (web imports them). Per-feature `schema.ts` holds only **route request/response validation** (or re-exports from shared). DTOs do **not** move into `packages/api`. |
| DB types       | **No** `database.types.ts` — keep hand-written shared DTOs authoritative (no codegen step, one type authority).                                                                                                                                       |
| Validation     | Adopt **`@hono/zod-validator`** in controllers, replacing the manual `parseJsonBody`/`safeParse` in `lib/http.ts`.                                                                                                                                    |
| Logging        | Add **`pino`** via `middleware/logger.ts`.                                                                                                                                                                                                            |
| Errors         | Centralized `middleware/error.ts`: services throw typed errors, the middleware maps them (absorbing today's `mapDbError` code-inspection: `23505`/`23503` → 409, default → 500 + server log).                                                         |
| JWT            | Extract verification into `lib/jwt.ts`; `middleware/auth.ts` consumes it (still `jose`).                                                                                                                                                              |
| Behavior       | Preserving. HTTP contract, status codes, and response shapes unchanged; existing route tests move to `features/<domain>/` and keep asserting the same behavior.                                                                                       |

## New dependencies

- `@hono/zod-validator` (route validation), `pino` (logging). `zod`, `jose`,
  `@supabase/supabase-js` already present.

## Provisional phases (finalized by spec-plan at activation)

1. **Infra + template feature** — `config/`, `lib/{jwt,response}.ts`,
   `middleware/{logger,error}.ts`, add deps, split `app.ts` from `index.ts`; migrate **one**
   feature (`accounts`, smallest) end-to-end as the reference pattern; its test moves and
   passes.
2. **Migrate remaining features** — `transactions`, `categories` (hierarchy validation →
   service), `budgets`, `subscriptions` (log RPC → service), `favorites`, `analytics` to the
   layered shape; move colocated tests. May split complex (`categories`, `subscriptions`)
   from simple domains.
3. **Cleanup + docs** — delete `routes/`, `lib/http.ts` leftovers, `db/`; verify no dead
   code; re-baseline `CLAUDE.md`/`AGENTS.md` BE architecture section (again — `foundation`'s
   F8 pass predates this structure).

## Constraints

- Integration branch `develop`; stacked phases. `terse-commit` before commits.
- Strictly behavior-preserving — the agent gate leans on the **existing route test suite**
  passing unchanged after each feature migrates (strong safety net for a refactor).
- Keep money/domain logic in tested TS; do not regress the `foundation` date/RPC work.

## Non-goals

- No new endpoints or behavior changes (pure refactor).
- No generated `database.types.ts`.
- No auth-flow / deployment changes (that's `be-integration`'s domain).
- No runtime swap (stays Hono on Node per current `@hono/node-server`; the `be-integration`
  PLAN's "Bun" note is aspirational and out of scope here).
