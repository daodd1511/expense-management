# Docs Dashboard — Plan

Produced via /grill-me interview, prompted by
https://spin.atomicobject.com/html-spec-dashboard/. All decisions below were
explicitly confirmed; do not reinterpret or expand scope during implementation.

## Problem

`docs/` now holds 19 spec folders (`PLAN.md` + often `EXECUTION.md`), 3 ADRs,
2 design docs, `BACKLOG.md`, `docs/PLAN.md`, and root `CONTEXT.md`. Browsing
all of it means opening files one at a time in an editor; there is no single
place to see everything at a glance or jump between docs quickly.

## Goals

- A script that generates one self-contained HTML file rendering all of
  `docs/` (plus root `CONTEXT.md`) for local viewing in a browser.
- Regenerable on demand: add/edit a doc, rerun the script, refresh the page.
  No manual dashboard edits, no build pipeline.
- A specs board (status/phases/debt/description) at the top, matching the
  data already computed by `scripts/spec-index.mjs`.
- A live text filter over the nav/board, since 19+ specs plus ADRs/design/
  backlog is too much to scan by scrolling alone.
- Auto-open the generated file in the default browser after writing it.

## Non-Goals

- No npm dependency for markdown rendering — hand-rolled Node-side converter.
- No collaboration features (highlight-to-comment, feedback export) from the
  source article — this is a solo repo, not a two-person review workflow.
- No hosting/deployment. Purely local; `docs/dashboard.html` is not committed
  (the repo's only deploy pipeline ships the app itself to a VPS, not docs).
- Does not replace `scripts/spec-index.mjs` / `docs/specs/INDEX.md`. That
  stays exactly as-is (committed, git-diffable, tied to the CLAUDE.md rule
  that STATUS-block edits regenerate and commit it in the same commit). The
  new script reuses its STATUS-parsing logic rather than recomputing status
  a second way.
- No client-side markdown rendering — conversion happens once at generation
  time in Node; the output HTML has no runtime markdown dependency.

## Product Decisions

- **Scope**: all of `docs/` — `docs/specs/*` (board + per-spec pages),
  `docs/adr/*`, `docs/design/*`, `docs/BACKLOG.md`, `docs/PLAN.md`, and root
  `CONTEXT.md`.
- **Output**: single file `docs/dashboard.html`, gitignored, regenerated by
  `pnpm docs:dashboard` → `node scripts/docs-dashboard.mjs`.
- **Markdown → HTML**: a hand-rolled converter in the new script (no `marked`
  or similar). Must correctly handle the constructs this repo's docs actually
  use: GFM tables, `- [ ]`/`- [x]` checklists, fenced code blocks (with and
  without a language tag), headers, bold/italic/inline code, links, and
  horizontal rules. Verify against real files before considering this done —
  STATUS blocks and PLAN.md tables are exactly the fiddly cases a naive
  regex parser breaks on.
- **Structure**: single HTML file acting as a one-page app. A nav (grouped:
  Board, Specs, ADRs, Design, Backlog, Context, Product Plan) shows/hides
  sections via vanilla JS — no actual multi-page navigation, no routing
  library.
- **Specs board**: same columns as `docs/specs/INDEX.md` (Status, Phases,
  Debt, Description), rendered as an HTML table, each spec name linking to
  its section further down the page. Computed by importing/reusing
  `scripts/spec-index.mjs`'s STATUS-block parser, not reimplementing it.
- **Per-spec page**: tabbed — a "Plan" tab and, if `EXECUTION.md` exists, an
  "Execution" tab (click to switch, vanilla JS). Specs with `PLAN.md` only
  show just the Plan tab.
- **Search**: a single text input filters nav entries and specs-board rows
  live as you type (plain JS substring match on title/status — no fuzzy
  search library).
- **Auto-open**: after writing the file, the script shells out to open it in
  the default browser (macOS `open`); if that fails, fall back to just
  logging the file path — never treat a failed auto-open as a script error.

## Judgment Calls (not asked, noted here)

- `docs/BACKLOG.md`'s Fixes/Features/Ideas grouping needs no special code —
  it's already `##` headings in the source file, so the same markdown
  renderer that handles everything else produces the grouping for free.
- Styling is plain/minimal (system font stack, basic table/code borders) —
  this is an internal dev tool, not reusing the app's Kanagawa theme tokens.

## Scope of Work

1. `scripts/docs-dashboard.mjs` — new script:
   - Hand-rolled markdown-to-HTML converter (tables, checklists, code
     fences, headers, inline formatting, links, hr).
   - Reuses `scripts/spec-index.mjs`'s STATUS-block parsing for the board
     (extract the parsing function so both scripts can import it, or import
     `spec-index.mjs` directly if its parser is already a plain exported
     function — check current shape before deciding which).
   - Walks `docs/specs/*`, `docs/adr/*`, `docs/design/*`, `docs/BACKLOG.md`,
     `docs/PLAN.md`, root `CONTEXT.md`; renders each to an HTML fragment.
   - Assembles one HTML document: nav + filter input + board + all doc
     sections (tabbed for specs with both Plan/Execution).
   - Writes `docs/dashboard.html`; shells out to open it (macOS `open`),
     falling back to logging the path on failure.
2. `package.json` — add `"docs:dashboard": "node scripts/docs-dashboard.mjs"`.
3. `.gitignore` — add `docs/dashboard.html`.
4. `CLAUDE.md` — add `pnpm docs:dashboard` to the Commands section.

## Verification

- Run `pnpm docs:dashboard`, open the result, and manually check: every spec
  appears with working Plan/Execution tabs, the board's status/phase/debt
  matches `docs/specs/INDEX.md`, a STATUS block's checklist renders as an
  actual checklist (not raw `- [x]` text), at least one table (e.g. from
  `docs/PLAN.md`'s Scope & Stack table) renders as an HTML table, and a
  fenced code block renders as a code block. The filter input narrows the
  nav/board when typed into.
